Architecture decisions

The project folder belongs to the user. Brig runs the agents. Tugboat connects these systems and owns the records that let a user return to a chat.

These architecture decision records (ADRs) describe Tugboat's design and how it changed. Links between decisions identify changes to earlier behavior. An inferred reason explains what the code does. A recorded reason comes from a project document, implementation comment, or test.

Desktop and runtime

ADR-001 · Use a Tauri window with a native command boundary

Vite builds the TypeScript interface for a Tauri 2 webview on Apple silicon Macs with macOS 15 or later. Rust registers named commands for project, account, storage, and terminal operations. Native events tell the interface when state changes.

Reason (inferred)
The interface can show the same project and session in several views. One native owner can verify a request against the current records and Brig state.
Consequence
A new command needs a Rust handler and matching frontend arguments. The main window restricts navigation and denies new webview windows. The configured capability grants event listening and removal of listeners. Provider sign-in opens the system browser.

Source files · Command registration and window navigation · Window and content security policy · Main window capability · Frontend state store

ADR-002 · Give each terminal a native surface and a process

Rust starts the process on a pseudo-terminal (PTY). An AppKit view uses libghostty-vt for terminal emulation. The webview requests placement, focus, visibility, and closure by terminal ID. Switching chats brings the selected surface back with its scrollback.

Recorded reason
Chats need interactive text input, approval prompts, keyboard signals, and the ability to continue while the user views another chat.
Consequence
Process exit and surface disposal are separate events. Diagnostic output can remain visible after the process exits. The app limits live processes to 16 and retained finished views to 32. Terminal changes can affect the PTY, the native view on the main thread, and the TypeScript layout controller.

Source files · Product behavior · Terminal registry and limits · PTY lifecycle · AppKit surface · Layout queue

ADR-003 · Ship a pinned Brig runtime with the app

An empty Brig path selects the bundled executable. Tugboat includes Brig, hull, the virtual machine runners, cosign, and the required ext4 disk tools. Build scripts check pinned inputs. A manifest records the packaged files and their hashes. The Mac check validates the runtime and checks the Brig version.

Recorded reason
The packaged runtime can prepare public guest images on a Mac without Homebrew. Patches make the disk tools available inside the app and support shared folder paths that contain spaces.
Consequence
A saved absolute path can select a compatible Brig executable. An invalid override gives an error. A release still needs the other bundled tools. The first guest start can need internet access for images and boot assets. The bundled registry configuration keeps public image pulls separate from the host Docker credential store.

Source files · Runtime requirements · Release input pins · Runtime assembly · Manifest verification · CLI selection and checks · Registry configuration

Environment startup presentation

ADR-021 · Reserve a bounded native terminal area for boot status

A centered web card shows setup status, elapsed time, and a bundled Three.js animation. On first startup, the card appears in the project workspace. Opening the setup terminal moves it to the terminal surface, where the native layout accepts the card rectangle.

Recorded reason
The AppKit terminal is above the webview. A web stacking order cannot cover it. A bounded drawing exclusion reveals the status card while keeping setup output visible around it.
Consequence
Rust validates the rectangle. AppKit clips drawing and pointer input to the terminal bounds. Omitting the rectangle restores the full surface. Startup presentation follows project, environment, and terminal identity. Navigation releases the animation without stopping the process. Reduced motion uses a still frame. After successful setup, the terminal closes when its process exits. If setup fails, Tugboat retains the available output.

Boot presentation · Three.js scene · Native layout contract · Drawing exclusion · Native drawing and input checks

Projects and environments

ADR-024 · Stop registered project environments before the app exits

Closing the main window, quitting from the app or Dock, and restarting use the same shutdown path. AppKit waits for the outcome before closing the application. A Brig guest can continue running after its terminal exits. Tugboat therefore stops its registered project guests after it saves final usage. It verifies each target against the project folder, Brig reference, sandbox name, and persistent guest home.

Only the shutdown worker can issue host commands during this step. A failed stop keeps the app open. A retry checks the live inventory and completes outstanding stops. Saved files and chats remain available when the project reopens.

Desktop shutdown · Project environment shutdown

ADR-023 · Prepare the guest automatically for a connected provider

Decision
A successful Mac check and a connected account for the selected agent allow automatic first startup. Tugboat checks the project policy, starts or reuses the shared guest, and checks both agents.
Reason
New Chat specifies the project and the agent. The saved project settings provide the inputs for guest setup.
Consequence
A pending chat opens when its agent is ready. A recorded first-start failure can trigger up to three retries with the same plan. Wait for the previous setup terminal to exit before retrying. Cancel preparation, Stop, and project switches clear pending retries. The project shows the final error and recovery actions.

Automatic startup and retry · First-chat checks

ADR-022 · Give each project one shared Brig environment

This decision replaces the per-agent environment model in ADR-004 and the historical import in ADR-015.

Decision
The project derives one environment ID and owns its verified Brig reference, image digest, guest home, lifecycle, and network policy. Both agents can use the same files and guest processes. The chat identity includes the agent kind and native session ID.
Reason
One guest keeps common project work available to either agent and gives the user one project plan to review. The app keeps renewable provider sign-in on the Mac.
Consequence
Codex and Claude launch and resume independently within the shared guest. Stop ends both agents’ guest processes. Reopening an approved unchanged plan reuses its identity. Existing registrations keep their paths and start with empty history after verified retirement of former Tugboat-owned storage.

Project record · Shared Brig profile · Usage keys · Reset and recovery

ADR-004 · Register a folder once and identify each agent environment separately

Superseded by ADR-022. This decision originally assigned one environment to each agent of a registered folder.

Recorded reason
The user can work on the same folder with either agent. Each agent needs its own guest home, policy, lifecycle, and chat history. Disk remounts must preserve the connection to the original project.
Consequence
CPU count, memory, and image verification are project settings. Network mode, policy, and preparation state belong to each environment. Changing shared resources invalidates preparation for the other environment. A different folder at the saved path fails the identity check. Two agents can use the same native chat ID in distinct environments.

Source files · Folder identity and registry · Former registry decoder

ADR-005 · Verify the Brig execution plan before starting work

Rust resolves the saved project and shared environment. It compares the current Brig policy to the saved fingerprint, a hash of its contents. It validates the execution plan and derives a second fingerprint from the project, environment, profile, and executable plan fields.

Reason (inferred)
A policy, folder, or running guest can change after the interface shows a preview. A process launched from an old preview could act on a different target.
Consequence
A valid plan identifies the expected writable project share, hull/hvi runtime, profile, session, network mode, resource limits, and image verification setting. It must satisfy the checks on credentials, host skills, published ports, and private record paths. A changed fingerprint requires a new preview. Guest operations use the verified environment. Open local terminal explicitly starts a Mac shell in the host project folder.

Source files · Checked environment and plan fingerprint · Brig plan validation · Session launch checks · Local shell command

ADR-006 · Apply the network policy to a specific Brig environment

New settings use isolated networking and agent-specific host lists. The user can select offline mode. The app requires a bound policy that denies other outbound traffic by default. ADR-030 adds one exception for all public internet access. Changing application defaults affects new policies. Editing an existing policy requires the stopped environment and the current policy fingerprint.

Recorded reason
Different agents need different service hosts. The project owner can review the actual policy and its binding independently of the application defaults.
Consequence
The editor limits changes to supported, owned policy documents and bindings. Guest host rules apply to resolved addresses. Two services can share an address, so a boundary test can report an inconclusive result. Provider sign-in on the Mac and provider-hosted tools have separate network paths.

Source files · Network behavior · Agent defaults · Policy edits · Ownership rules · Boundary checks

ADR-007 · Keep agent permission modes in each agent adapter

Both agents run inside Brig. New and resumed Codex chats default to --sandbox danger-full-access --ask-for-approval never. The alternative uses workspace-write with command network access disabled and the same approval setting. Claude Code uses --permission-mode manual. ADR-026 replaces the Claude mode for new chats. ADR-029 makes both agent modes project settings.

Recorded reason
Brig supplies the outer file and network boundary. Codex supports a second workspace restriction. Claude supplies its own interactive permission flow.
Consequence
The default permits Codex to act throughout its guest and to write the shared host project folder. Claude can ask the user to approve or deny an action. The launch path checks the supported capabilities of the selected guest program. Boundary checks report observations independently of the selected permission mode.

Source files · Guest access settings · Codex arguments · Claude arguments · Claude capability check · Agent boundary contract

ADR-008 · Retain ownership and progress through environment removal

The app records ownership of the session, binding, and policy separately. Preparation refuses a new project if an existing session uses its reserved reference. Removal previews the shared environment and checks the fingerprint and typed confirmation against the current target.

Reason (inferred)
A user can manage Brig outside Tugboat. A removal request spans several external operations. An interruption can leave some steps complete.
Consequence
Removal saves its progress through optional guest sign-out, environment removal, binding cleanup, policy cleanup, and record removal. A retry checks the live target again. Shared or externally changed policies survive cleanup. Forget removes the project registration and retains its project files, guest resources, and saved usage. A confirmed environment removal can remove its guest home.

Source files · Current project preparation · Preview scope · Removal checkpoints · Cleanup and recovery · Forget operation

Provider accounts

ADR-009 · Keep one renewable host account per provider

Tugboat stores renewable credentials in private files under the active records folder. ChatGPT uses chatgpt/session.json. Claude uses claude/session.json. A verified project guest can receive an access copy for each agent. The host retains the refresh tokens.

Recorded reason
The user can sign in once across projects while each environment keeps its own configuration, policy, history, and lifecycle.
Consequence
Shared Codex sign-in requires the standard guest credential directory. New chats disable the shared Codex daemon to avoid retaining earlier credentials. Managed Claude guests receive an access copy in memory through the guest helper. The helper preserves independent connector records. Project removal preserves the host accounts. Shared sign-out checks active sessions for the affected provider.

Source files · Shared account behavior · Codex guest eligibility · Codex access copy · Shared guest mounts · Claude guest update

ADR-010 · Run browser authorization from the Mac

The account command starts a native sign-in attempt for the selected provider. ChatGPT uses device authorization. Claude uses Proof Key for Code Exchange (PKCE) and a temporary loopback callback. Rust opens the provider page, verifies the response, exchanges credentials, and saves the account.

Provider sign-in starts from Settings. The shared provider records own cancellation and account publication.

Recorded reason
Settings must let a user connect before adding a project or starting a guest. The authorization attempt has its own lifetime, including cancellation.
Consequence
The webview receives the phase, browser address, optional device code, and message. Rust owns secret protocol values and checks the attempt ID before accepting a late result. The user can cancel until saving begins. A connected guest still uses its environment policy for model requests.

Source files · Provider settings · Provider protocols · Loopback callback · Attempt state and public status · Attempt ownership checks

Conversations and usage

ADR-011 · Resume from agent transcripts and group verified descendants under the root chat

Codex owns its rollout files. Claude owns its persistent transcripts. Readers associate the native session and working directory with the verified environment. A conversation graph links a subagent to its parent when the records support that link. Normal forks remain separate chats.

Recorded reason
The session list must show each root once and include its nested agents. A title or a shared project path alone cannot establish a parent.
Consequence
A root can resume when the required source and environment checks pass. Claude new chats receive an app-generated session ID. Codex generates its own ID. An unresolved child goes to read-only recovery. Archive and Trash change the root's saved state. They preserve native transcripts, child records, and project usage.

Source files · Root and subagent behavior · Relationship checks · Claude parent evidence · Claude resume check · Saved state and details

ADR-012 · Count recorded work by source identity and carry missing data into totals

For a Codex request with source evidence, the identity includes the verified guest namespace, provider, origin thread ID, and response ID. Claude merges repeated message observations using stable identifiers. Family totals include verified descendants. Saved evidence distinguishes unknown consumption from a measured zero.

Recorded reason
Forks can copy past Codex events. A Claude transcript can contain several observations of one response. An incomplete transcript can omit a request or a child.
Consequence
Equal token counts or equal native session IDs in separate environments cannot establish duplicate work. Saved usage can remain available after a transcript disappears. Claude coverage remains partial and the reader cannot attribute its usage to individual user prompts. A source coverage label describes the available local evidence.

Source files · Usage contract · Physical request key and totals · Copied Codex history · Claude measurement and merge · Family details

ADR-013 · Save dated rates, assumptions, and corrections with each priced request

The usage layer calculates a token cost estimate from recorded counts and the applicable provider rates. It keeps the date, rates, and pricing evidence with the request. Different cache lifetimes, service tiers, and provider rules can produce different estimates.

Recorded reason
The user needs a reproducible estimate even after a catalogue update or loss of the source transcript. The evidence must show which rates were known and which values the calculation assumed.
Consequence
New catalogue rates apply when pricing eligible requests. Historical repricing and count corrections require evidence. Saved Claude counts can receive prices offline. Invalid pricing inputs stay unpriced. Project totals can contain a known subtotal and additional unpriced work. The estimate excludes subscription charges, account discounts, tool charges, and taxes.

Source files · Cost estimate scope · Rate snapshots and corrections · Claude tariffs · Price evidence · Offline pricing transaction

Records and recovery

ADR-035 · Keep network activity in the project records

The isolated gateway is the source for recorded flows, policy decisions, and traffic counts. Guest kernel events can identify an executable and a launch control group. Tugboat saves the gateway’s structured revisions in the records database.

Recorded reason
Gateway diagnostics omit successful traffic and disappear at Stop. A destination or time alone cannot identify the process that sent traffic.
Consequence
Queue files remain available until Tugboat commits their revisions and offsets. The database scopes reads by project and environment. Missing process evidence leaves the gateway row available. The recorder persists connection metadata and excludes traffic content.

Network activity data flow · Brig gateway and launch binding · Import and page reads

ADR-014 · Store usage facts for both agents in one database per records folder

The active usage.sqlite3 holds environment keys, session records, turns, requests, historical corrections, and parser positions. It stores per-session summaries for dashboard reads. Configuration, account records, profiles, location metadata, and native transcripts retain their own formats and owners.

Recorded reason
Adding one request or changing one chat state used to require a whole ledger rewrite. Session and request rows allow smaller reads and writes. One transaction can commit both a measurement and the parser position that produced it.
Consequence
Runtime access uses a shared database handle. The store checks the dataset identity and its file binding. It enables foreign keys, a rollback journal, and extra synchronization. Each durable write has a synchronization cost, even for a small append. If a commit result is uncertain, the next access must verify the database before processing resumes.

Source files · Database schema · Shared database handle · Identity and recovery checks · Transactions · Scoped scanning

ADR-015 · Activate the SQLite writer only after verifying the legacy import

Superseded by ADR-022. This decision documents the original SQLite activation that imported saved JSON ledgers.

Reason (inferred)
Restarting between publication steps must preserve a recoverable dataset. Enabling the new writer before validation could accept incomplete facts or lose a later update.
Consequence
After activation, SQLite owns new writes. Original JSON files can be older than the database. An absent, damaged, or mismatched active database blocks usage access. Recovery requires the verified active dataset or a matching SQLite backup. A marker change or a legacy ledger alone cannot recover later SQL writes.

Source files · Current activation · Directory marker

ADR-016 · Move records as a verified dataset on restart

Tugboat resolves the active records folder before opening usage storage. The default folder under ~/Library/Application Support/Tugboat holds the location pointer and its lock. A move records the intended destination first. On restart it copies the closed dataset, verifies it, marks the target complete, commits the pointer, and cleans the old location.

Recorded reason
A removable disk can disappear at any stage. Settings, project identities, provider accounts, usage, and backups must continue to refer to the same dataset.
Consequence
An incomplete target cannot become active. A missing disk leaves recovery available. Locate checks the dataset ID. SQLite checks include integrity, foreign keys, and matching copy hashes. Private records must stay outside project shares and guest homes. Moving records leaves Brig guest homes and their transcripts in place.
An explicit switch to existing records pins the selected dataset ID. Startup verifies and locks that dataset before it commits the pointer. It keeps the former dataset in place.

Source files · Records location contract · Move and locate transactions · Move states · Closed database verification · Record publication

ADR-017 · Give asynchronous workflows explicit states and a defined owner

Native code owns environment operations, sign-in attempts, storage state, and shutdown. The interface tracks which request and project own a pending screen update. For example, a dashboard reply can arrive after the user has selected another project. The request revision lets the controller reject that reply.

Recorded reason
A workflow can fail, finish late, or receive a second request while work is still pending. Its current state determines which transition can succeed.
Consequence
Shutdown requests confirmation when a process is running. After approval, the app drains processes, waits for account writes, records final usage, stops its registered project environments under ADR-024, and closes storage before exit or restart. A failed final scan or database close interrupts shutdown. Implementations must handle the partial effects, including a process that already exited.

Source files · Repository workflow rules · Dashboard updates · Request revisions · Environment operation ownership · Shutdown ordering · Exit permission

Build and distribution

ADR-018 · Separate pull request checks, installer publication, and Apple distribution verification

Pull request jobs have read-only repository permissions. They run the web checks on Linux. Changes to native dependencies or source trigger macOS checks. A separate workflow for pushes to trunk builds the Apple silicon disk image (DMG), checks the packaged runtime, and publishes it with a build-specific tag.

Reason (inferred)
Frontend tests can run without a Mac. Native terminal, filesystem, virtual machine, and packaging behavior need macOS tools. Publishing an installer requires separate write access.
Consequence
The original trunk workflow used an ad hoc signing identity. Its package checks established the version, disk image, and bundled runtime. Developer ID distribution used a separate signing and notarization script. The release verifier checks Apple tickets and Gatekeeper on a mounted installer. Upstream runner signatures have their own verification step. ADR-019 replaces the release trigger and connects Apple signing and verification to publication.

Source files · Pull request checks · Trunk publication · Bundle settings · Developer ID release script · Apple distribution checks · Runner checks

ADR-019 · Require a release marker and Apple verification before publication

This decision replaces the release trigger and signing path in ADR-018. A push to trunk starts the release jobs only when its latest commit message contains new-release. The match ignores letter case. The workflow passes six repository secrets to the existing Developer ID release script.

Recorded reason
The release commit must explicitly request a build signed with an Apple Developer ID certificate and notarized by Apple. Routine pushes must not publish installers.
Consequence
Tests and package verification must succeed before the publication job can run. Missing signing credentials, rejected notarization, invalid signatures, or failed Gatekeeper checks stop publication. A push without the marker skips both release jobs. Pull request checks retain their existing behavior. ADR-025 adds updater assets and signing.

Source files · Release condition and publication dependency · Signing and notarization · Apple distribution checks · Ordered secret setup

ADR-020 · Give development its own app identity and records

Tauri development runs use the name Tugboat Dev, the identifier sh.brig.desktop.dev, and their own default records folder. Only packaged builds can migrate the installed app’s legacy records. Brig commands in development use a separate home for telemetry settings, policies, and guest data.

Both apps can run at the same time. Each owns its records lock and can select a custom records folder independently.

Development identity · Records startup · Brig command environment

ADR-025 · Verify the app update before starting the approved shutdown

The production Mac app owns the feed, public key, package, and approval. The interface shows release information and active sessions. A check reads only the manifest. Approval binds the selected release and displayed sessions.

Recorded reason
Users can check without interrupting work. A failed transfer or signature check leaves active sessions available.
Consequence
After verification, Tugboat checks active sessions while it blocks new terminal starts. It asks again if a new session started. The existing shutdown sequence runs before replacement. The restart process waits for the old app to release its records lock. It checks that the approved version opens its window and the original records. It can show recovery if the new app fails to start. Publication checks that the signed disk image and update archive contain the same app.

Update checks · Update shutdown · Signed publication

ADR-026 · Start new Claude Code chats in auto mode

This decision replaces the Claude mode for new chats in ADR-007. New Claude Code chats start with --permission-mode auto. Resumed chats continue to use --permission-mode manual. ADR-027 replaces the mode for resumed chats.

Recorded reason
Users want new chats to start in auto mode by default. Brig still supplies the outer file and network boundary.
Consequence
Claude Code decides which actions to approve without a permission request in the terminal. The user can change the mode in the running chat. The launch path checks that the guest program supports the mode for the selected action. A guest without auto cannot start a new chat.

Claude arguments · Claude capability check

ADR-027 · Resume Claude Code chats in auto mode

This decision replaces the Claude mode for resumed chats in ADR-026. New and resumed Claude Code chats start with --permission-mode auto.

Recorded reason
Users want auto mode by default in every Claude Code chat. A chat that started in auto mode also continues in auto mode.
Consequence
Tugboat does not start Claude Code chats in manual mode. The user can change the mode in the running chat. A guest without auto cannot start or resume a chat. ADR-029 lets a project select manual mode again. Auto mode stays the default.

Claude arguments · Claude capability check

ADR-028 · Hide Claude Code Git attribution by default

Each project saves one Claude Code attribution value: hidden or shown. The default is hidden, also for projects that existed before this decision. When the value is hidden, new and resumed Claude Code chats start with --settings {"attribution":{"commit":"","pr":""}}. When the value is shown, Tugboat adds no settings argument. ADR-032 adds the status line to the same settings document, so every chat now has --settings; only the attribution part depends on this value.

Recorded reason
Users do not want Claude Code attribution in Git commits and pull requests by default. A project setting must not depend on a file in the user's project folder.
Consequence
Command-line settings take priority over the Claude Code settings in the project folder and in the guest home. A project cannot turn attribution on with its own settings file while the value is hidden. The Project settings switch changes the value without stopping the environment. Running chats keep their arguments until they start or resume again. A guest without --settings cannot start or resume a chat while the value is hidden. The registry writes the field only for shown. An older Tugboat version rejects a registry that contains shown.

Claude arguments · Claude capability check · Project record · Attribution switch

ADR-029 · Save agent command options for each project

Each project saves three agent options: the Claude Code permission mode (auto or manual), the Claude Code attribution from ADR-028, and the Codex boundary (brig or workspace). The defaults are auto, hidden, and brig. The launch path reads the values from the project record when a chat starts or resumes. The frontend no longer sends a boundary value with each launch.

Recorded reason
Users want to change agent command options for one project without changing other projects. The earlier Codex choice was a view state that reset after a plan change, so a new launch could silently use a different boundary.
Consequence
The Agents section of Project settings changes the values without stopping the environment. Running chats keep their arguments. A guest that does not list the selected permission mode cannot start or resume a Claude Code chat. The registry writes each field only when it differs from the default, so existing records stay unchanged. An older Tugboat version rejects a registry that contains a non-default value.

Agent settings · Claude arguments · Codex launch · Project record · Agents section

ADR-030 · Allow all public internet access only through the owned project policy

This decision adds one exception to the deny-by-default rule in ADR-006. The Network section can save the project policy with default: allow. The plan check accepts an allow default only when Tugboat owns the project policy, no other policy is bound, and the merged plan has no deny rules. Tugboat keeps the allowed hosts in the document, so the package manager and domain choices apply again when the user turns public access off.

Recorded reason
Some projects need destinations that a host list cannot predict. The user chooses this per project, and the default stays deny.
Consequence
Brig merges bound policies with the strictest default, so a second policy turns the run back to deny. Tugboat refuses to save public access while a GitHub access grant exists and reports when another policy restricts it. Boundary checks report an allow-default policy as inconclusive. Package manager domains are a fixed list of registry hosts in the policy, not a separate rule type. HTTP secrets and environment variables are not part of this decision.

Network access · Policy document · Plan check · Network section

ADR-031 · Stop the environment automatically before a settings change

Network changes and General saves still need a stopped environment, as in ADR-006. The interface now stops it first. When no guest process is working, Tugboat stops the environment without a question. Idle Codex chats close and stay resumable. When a guest process can be working, Tugboat lists the processes and asks before it stops them. The native policy guard counts the same guest processes that stop_project ends, so a Mac terminal no longer blocks a policy change.

Recorded reason
Users received a refusal that told them to stop the environment by hand, even when nothing was working. A working agent turn or command must not end without a warning.
Consequence
Only Codex reports a busy state through its terminal title. Tugboat treats every Claude Code chat, guest terminal, startup, sign-in, Git command, and test run as working. A guest that starts between the check and the change still causes the native refusal, and the user can retry. A rename in General does not stop the environment. The native save checks for a stopped environment only when CPU, memory, image verification, or network mode changes.

Stop gate · Stop impact · Running check · Policy guard

ADR-032 · Save model options and set the status line for each chat

This decision extends ADR-029. Each project also saves optional agent arguments. Claude Code: --model, --effort, --fallback-model, and --append-system-prompt. Codex: --model and -c model_reasoning_effort (low, medium, high, xhigh, max, or ultra). The Agents section offers fixed model lists from the model data checked on 2026-11-23: current models by full model ID and older models in their own group. The native save refuses ultra for gpt-6-luna and gpt-5.6-luna. Tugboat also adds a fixed status line to every new and resumed chat. Claude Code gets a statusLine command in the --settings document. The command is a short python3 script that prints the model, effort, input and output tokens, context left, and the 5-hour and 7-day limits left. Codex gets -c tui.status_line with model and reasoning, context left, input and output tokens, and the 5-hour and weekly limits.

Recorded reason
Users want to choose the model and effort for one project, and to see usage in every chat without setting it up again.
Consequence
The record writes claudeOptions and codexOptions only when a value is set. Model names are validated and cannot start with a dash. The appended prompt uses the joined --option=value form. The launch path refuses a selected Claude option or a Codex model that the guest help text does not list. Every Claude chat now needs --settings. The Claude status line fields come from the input schema in the Claude Code 2.1.318 binary; the guest pins 2.1.326. The Codex status line item names were not verified against Codex 0.171.0 when this decision was recorded, and Tugboat passes them to every Codex chat at the user's request. A wrong item name can stop Codex chats from starting, so check a Codex chat after each Codex update.

Claude arguments · Claude status line · Codex arguments · Option values · Agents section

ADR-033 · Set the agent and network values of a new project in application Settings

The New projects section of application Settings supplies the starting values for new projects. settings.json has an optional projectDefaults record with the agent settings of ADR-032 and the network access of ADR-030. Tugboat copies the agent settings into the project record when the user adds the project. Preparation writes the network access into the project policy when it creates that policy for the first time. The deny default stays the default value.

Recorded reason
Users want to set their usual model, permissions, and network access once, instead of in each new project.
Consequence
Existing projects and existing policies keep their values. A change to the network defaults between adding a project and its first preparation applies to that project. If the policy creation was interrupted and the defaults changed, the template check refuses the policy and keeps the document. The settings file keeps schema version 2. Rust leaves out projectDefaults while it has its default values, because an earlier Tugboat refuses unknown fields. After a user saves other values, an earlier Tugboat cannot read the settings file.

Project defaults · Registration · First policy · New projects sections · Settings dialog

ADR-034 · Update each coding agent when the project guest starts

New projects boot a signed, agent-free image. Project registrations keep their own image digests. Tugboat verifies the running environment before enabling its terminal. It checks each vendor once per Linux boot ID and activates each compatible agent independently.

Recorded reason
A stable agent release can arrive between Tugboat releases. Package downloads must respect project isolation and allow the terminal to open during installation.
Consequence
The Mac verifies and caches packages. A project activates a versioned directory with an atomic link change after guest checks pass. Failed updates can retain a previously verified version. Agent releases use the same persistent chat and credential paths.

Startup checks · Release signatures

When a change replaces a decision, keep its ID and link to the replacement. Record the changed behavior, the reason, and the source that implements it.
